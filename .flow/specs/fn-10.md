## Overview

Replace the custom `BroadcastService` SSE implementation with river.ts's `RiverEmitter` and migrate the dashboard from SSE to WebSocket for full bidirectional communication. This unifies the real-time messaging layer across the cockpit system using **river.ts format everywhere**.

**Current State:**
- Dashboard ←--SSE--→ Hub ←--WebSocket (JSON-RPC 2.0)--→ Agent(s)
- Dashboard sends commands via REST API
- Custom `BroadcastService` with 28 usages across hub-server

**Target State:**
- Dashboard ←--WebSocket--→ Hub ←--WebSocket--→ Agent(s)
- **Unified river.ts format** for all WebSocket communication
- Bidirectional communication with `request()` support over single WebSocket connection
- Type-safe event schemas shared between all components

## Scope

**In Scope:**
- Replace `BroadcastService` with `RiverEmitter` or native WS broadcast
- Create dashboard WebSocket endpoint (`/ws/dashboard`)
- Migrate dashboard client from `RiverClient` (SSE) to `RiverSocketAdapter`
- **Extend river.ts with `request()` method** for RPC semantics
- Add reconnection with exponential backoff for dashboard WS
- Shared event type definitions in `@cockpit/core`
- **Migrate agent protocol from JSON-RPC 2.0 to river.ts format**

**Out of Scope:**
- WebSocket authentication (can add later)
- Multi-region/CDN considerations
- Event replay/sourcing for missed events

## Key Decisions (from interview)

### 1. Protocol Format: river.ts everywhere
**Why:** User (owner of river.ts) decided to unify on river.ts format instead of maintaining JSON-RPC 2.0 separately.

**Wire format:**
```typescript
// Events (no response expected)
{ type: "sdk:message", data: { instanceId, message } }

// Requests (expect response)
{ type: "instance.spawn", data: { cwd, model }, id: "req-123" }

// Response
{ type: "instance.spawn", data: { instanceId }, id: "req-123" }
```

### 2. Extend river.ts with `request()` method
Add RPC semantics to `RiverSocketAdapter`:
```typescript
interface RiverSocketAdapter {
  // Existing
  send(type: string, data: unknown): void
  on(type: string, handler: (data) => void): void
  
  // New
  request<T>(type: string, data: unknown, timeout?: number): Promise<T>
}
```

**Implementation:**
- Track pending requests in `Map<string, { resolve, reject, timeout }>`
- Add optional `id` field to outgoing messages
- Route responses by matching `id`
- Default 30s timeout

**Performance:** Negligible - just Map lookup + setTimeout per request.

### 3. Separate `/ws/dashboard` endpoint
- Agents connect to `/ws/hub`
- Dashboard connects to `/ws/dashboard`
- Different auth patterns, message types, routing logic

## Approach

### Phase 1: Extend river.ts (fn-10.0 - separate PR)
- Add `request()` method to `RiverSocketAdapter`
- Add `id` field support to wire format
- Publish new river.ts version
- **Note:** This may be done as a separate contribution to river.ts repo

### Phase 2: Shared Event Schema (fn-10.1)
Move event type definitions to `@cockpit/core`:
- Define all events using `RiverEvents` pattern
- Export types for both hub-server and dashboard

### Phase 3: Hub WebSocket Endpoint for Dashboard (fn-10.2)
Create `/ws/dashboard` endpoint using Elysia's `.ws()`:
- Client registration on connect
- Broadcast via `ws.publish()` pub/sub
- Request/response handling using river.ts format

### Phase 4: Dashboard Registry (fn-10.3)
Create `DashboardRegistry` service:
- Track connected dashboard clients
- Provide typed `broadcast()` method
- Handle client lifecycle

### Phase 5: Dashboard WebSocket Client (fn-10.4)
Replace SSE client with WebSocket using `RiverSocketAdapter`:
- Implement message routing to existing store handlers
- Add connection state management with reconnection
- Use `request()` for commands

### Phase 6: Command Migration (fn-10.5)
Move dashboard commands from REST to WebSocket:
- Spawn/stop instance
- Send message to instance  
- Permission responses
- Question answers

### Phase 7: Cleanup (fn-10.6)
- Remove `BroadcastService`
- Remove SSE endpoint (`/api/events`)
- Update all broadcast calls to use new WS broadcast

### Future Phase: Agent Protocol Migration
- Migrate agent ↔ hub from JSON-RPC 2.0 to river.ts format
- **Defer:** This is larger scope, do after dashboard migration proven

- [ ] All existing SSE events work over WebSocket
- [ ] Dashboard commands (spawn, send, permission, question) work over WS
- [ ] Reconnection works with exponential backoff

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| WebSocket blocked by corporate proxies | Keep SSE as fallback initially, remove after validation |
| river.ts `request()` not merged | Can fork/patch locally until merged |
| Agent protocol migration complexity | Defer agent migration, focus on dashboard first |
| Message ordering issues | Use sequence numbers if needed (defer until problem observed) |
